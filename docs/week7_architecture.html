lab5/src/lib/agent.ts
TypeScript ReAct Agent Loop
MAX_AGENT_LOOPS env var · plan → act → observe · hard ceiling enforced
▼
The core ReAct loop. Calls Claude with tool definitions, executes tool calls via HTTP to the Python backend, feeds results back into the conversation, repeats until stop_reason == end_turn or MAX_AGENT_LOOPS is hit. Returns structured AgentResult with typed step array for UI and observability.
// Loop limit — env var, never hardcoded (design decision) const MAX_AGENT_LOOPS = parseInt( process.env.MAX_AGENT_LOOPS ?? "5", 10 ); while (loopsUsed < MAX_AGENT_LOOPS) { loopsUsed++; const response = await client.messages.create({...}); if (response.stop_reason === "end_turn") { /* done */ break; } if (response.stop_reason === "tool_use") { /* execute tools */ continue; } } // Loop limit: graceful termination, partial result, never exception
Design decisions
MAX_AGENT_LOOPS from env var — adjustable without code change
Loop ceiling owned by agent code — server and model never see this value
Tool failure handled by system prompt tiering — not loop code (Option C)
Loop limit → graceful partial result, never empty string or exception
Every step emitted as typed AgentStep — UI and observability consume same data

Tool Failure Protocol — Criticality Tiering
TIER 1 — CORE
search_documents
If error returned: immediately stop. Do not attempt workarounds. Do not fabricate. Respond with explicit unavailability message. Research task cannot complete without this tool.
TIER 2 — SUPPLEMENTARY
get_current_weather
If error returned: note limitation, continue task. Include "Note: weather data was unavailable" in response. Task can complete without this tool.
TIER 3 — WRITE
save_reminder
If error returned: complete research task normally, note failure briefly at end. Does not affect research output quality.
Morgan's rule
The system prompt makes the right failure response the path of least resistance. Specific instructions prevent model improvisation in error states — and improvisation in error states is where hallucination lives.
Traditional vs AI-Native — Agent Orchestration
DimensionTraditionalAI-Native
Multi-step task execution Hard-coded workflow. Developer writes branching logic. Every path anticipated at design time. Agent decides which steps to take. Model is the router. New paths emerge from tool composition without new code.
Tool integration RPC/REST. Developer writes client, handles auth, maps response. Every integration bespoke. MCP. Tool describes itself. Model reads schema and knows how to call it. Same protocol for every tool.
Stopping condition Explicit — the function returns. The program ends. Must be designed. Without hard loop limit, agent runs indefinitely burning tokens. New failure mode.
Error recovery Try/catch, retry, raise to caller. Each tool must have explicit failure mode in system prompt. Model will hallucinate without instructions.
When to use agents Never — deterministic code handles orchestration. Only when: sequence unknown at design time, tool selection requires reasoning, iterative refinement helps.
MCP Protocol — Key Concepts
stdio transport
Host spawns server as subprocess. Communicates over stdin/stdout. Used with Claude Desktop. Local dev. MCP_TRANSPORT=stdio. stdout is the JSON-RPC channel — never print to it.
SSE transport
Server runs as long-running HTTP process. Client connects via SSE. Used for Cloud Run. MCP_TRANSPORT=sse. Production path. Same tool implementations — only transport adapter changes.

Key Findings
Finding 1 — The registry pattern from Week 4 is an MCP server without the network boundary
REGISTRY maps names to schemas and callables. get_tool_schemas() becomes list_tools(). dispatch() becomes call_tool(). The tool implementation files (weather.py, reminder.py, retriever.py) were untouched. Only the transport layer is new. This is what clean architecture buys across eight weeks of iteration. When new capabilities layer on top without changing what is already working, architecture is doing its job.
Finding 2 — MCP_TRANSPORT and ENVIRONMENT are orthogonal — coupling them would cost flexibility
The urge is to make MCP_TRANSPORT a derived value from ENVIRONMENT. Resist it. You need ENVIRONMENT=gcp MCP_TRANSPORT=stdio to run eval validation against real Claude with a local server. Two dimensions, two env vars. The config.py pattern from Week 1 applies: one switch per independently variable thing. This is the bootcamp's recurring lesson: architectural decisions at the seams matter more than implementation decisions inside components.
Finding 3 — stdout in stdio mode is a protocol channel, not a debug console
In stdio transport, stdout is the MCP JSON-RPC channel. Any print() to stdout corrupts the protocol and produces cryptic failures. All debug output must go to stderr: print("...", file=sys.stderr). This is a new constraint that doesn't exist in traditional server development. The rule: in any stdio-transport server, treat stdout as a binary protocol channel, never a log sink.
Finding 4 — Agent eval structure differs fundamentally from deterministic evals
The 20% of agent evals that can be exact assertions are the most valuable: structural guarantees (planning first, response never empty), loop limit enforcement (loopsUsed ≤ maxLoops), and failure mode injection (inject error dict, assert response contains unavailability language). The 80% that require probabilistic scoring — did the model choose the right tool? — still use substring matching on tool names in the step array, not prose quality scoring. The step structure makes this mechanical. Design your data structures for testability.
